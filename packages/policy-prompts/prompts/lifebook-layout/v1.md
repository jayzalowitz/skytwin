# System
You are choosing a layout for a per-domain detail page in a digital twin's "Lifebook" UI. Different life domains have different data shapes:

- **Health-like**: appointments, symptoms, prescriptions, lab results. Timeline matters; surface recent events first.
- **Project-like**: meetings, decisions, blockers, deadlines. Status snapshot + decision log.
- **Hobby-like**: events, photos, gear notes, locations. Browse-first; surface variety.
- **Job Search-like**: applications, recruiter messages, interviews, offers. Pipeline / funnel ordering.
- **Caregiving-like**: medication schedule, caregiver shifts, contact list. Schedule + people first.

You don't need to fit a domain into one of these — pick whatever ordering best surfaces the SPECIFIC signal-type distribution given. The signal histogram is your ground truth; the domain name is hint.

Available section types (you may use any subset, in any order; minimum 2):
- `timeline` — chronological signal feed (best when signals are dense and recent)
- `signals` — generic recent-signal list (always-safe fallback)
- `capabilities` — suggested MCP capabilities for this domain
- `entities` — extracted people / places / things relevant to this domain
- `decisions` — past twin decisions tagged to this domain
- `metrics` — counts / rollups (signal count, frequency, growth)
- `schedule` — upcoming calendar items in this domain
- `inline_edit` — inline edit affordance for extracted facts (rendered as a single section, not per-item)

# User
Pick a `layoutId` describing the chosen shape (e.g. `health-timeline`, `project-status`, `hobby-browse`) and order the sections so the most-informative-for-this-domain section comes first.

# Output
{
  "layoutId": string (short kebab-case identifier, max 64 chars),
  "sections": [
    {
      "type": one of the section types above,
      "title": string (user-facing heading, max 64 chars),
      "order": integer >= 0 (lower renders first)
    }
  ]
}

# Constraints
- Return at least 2 sections and at most 6.
- `order` values must be unique within the response.
- Never invent section types — pick from the listed set.
- When the histogram is sparse (< 3 distinct types or < 5 total signals), prefer the generic layout: `{layoutId: "generic-two-column", sections: [signals, capabilities]}` rather than a speculative shape.
- Return valid JSON only.

Yes, SkyTwin can run from a real Gmail inbox.

Use a Google OAuth app you create and control. The current alpha-0.6.106.0 release includes the setup wizard in its desktop window and serves the same page to authenticated local-browser sessions; current source retains the live connectors behind an explicit experimental operator flag.

Packaged alpha · desktop first

Download and start the current alpha, then open Connect Gmail in the desktop window. This is the reliable first-account path because Electron completes a one-use session handoff after Google consent. SkyTwin also serves the same page at http://localhost:3200/#/connect-gmail, but a fresh browser does not inherit that session; use the browser page only from an already paired or authenticated browser session.

Use a test Google account first.

The desktop alpha is unsigned. Its Google client secret is stored without app-level encryption in SkyTwin's configured database. The alpha's OAuth callback also writes access and refresh tokens to plaintext token columns, regardless of Credential Vault state. The requested Google scopes authorize more than the runtime capability claimed here: use the feature for live Gmail and Calendar ingestion, not as evidence of supported send, archive, or Calendar-mutation behavior.

Step 1

Create a Google Cloud project

Open Google Cloud project creation, create a project such as my-skytwin, and select it.

Step 2

Enable Gmail and Calendar APIs

Enable the Gmail API and Google Calendar API for that project.

Step 3

Configure the OAuth consent screen

  1. Open Google Auth Platform.
  2. Use External audience, name the app, and add your own address as support and developer email.
  3. Add the Gmail account you will connect as a test user.
  4. If the project stays in Testing, expect the authorization to expire after seven days. Publishing it to Production can make a personal grant durable, but Google may continue to show an unverified-app warning.

Step 4

Create a Web Application OAuth client

  1. Open Credentials and choose Create credentials → OAuth client ID.
  2. Select Web application, not Desktop app.
  3. Add both authorized redirect URIs:
http://localhost:3100/api/oauth/google/callback
http://127.0.0.1:3100/api/oauth/google/callback

Copy the generated client ID and client secret. Never post the secret in an issue, log, screenshot, or support message.

Step 5 · Packaged alpha

Paste, consent, and let the inbox sync

Keep the alpha running. Open SkyTwin's Connect Gmail page inside the desktop window. Paste the client ID and secret, choose Save & connect Gmail, and finish Google's consent screen in your system browser. The desktop receives the one-use completion handoff and stores its session before returning to the dashboard. An already authenticated browser session may use the same UI at http://localhost:3200/#/connect-gmail; simply opening that URL in a fresh browser does not transfer the desktop session and protected credential writes will return 401. The worker then uses Gmail's History API to ingest live inbox signals. Initial signals should begin appearing after the next polling cycle.

Current-source operator setup

Current source defaults closed. Put the following values in your local .env before starting SkyTwin: 

SKYTWIN_GOOGLE_CONNECTION_MODE=experimental
GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=your-client-secret
GOOGLE_REDIRECT_URI=http://localhost:3100/api/oauth/google/callback

Then run migrations and start the normal source services. The exact experimental value is required; credentials alone do not enable account routes. In current source the self-service credential wizard is intentionally hidden, so operator environment configuration is the coherent path.

To create the first user and request the Gmail scope tier, open this local API URL after the services are healthy: 

http://localhost:3100/api/oauth/google/authorize?newUser=true&include=gmail

The endpoint returns JSON containing a Google url. Copy that URL into your browser, complete consent, and let the callback return you to the local web dashboard at http://localhost:3200. You can use the dashboard in an ordinary browser; Electron is not required for this source path. This manual handoff is necessary because the current-source Connect screen deliberately continues to show the account-free preview boundary even when the operator flag is enabled. For an existing authenticated user, use the same endpoint with userId=<that-user-id> instead of newUser=true.

What access SkyTwin requests

  • openid, email, and profile to bind the grant to the Google identity.
  • calendar.readonly and calendar.events for Calendar data. Google's grant permits viewing and editing events on calendars the account can access.
  • gmail.readonly and gmail.modify when the BYO Gmail path is selected. Google's gmail.modify grant permits reading, composing, and sending mail in addition to changing mailbox state.

Those descriptions state the maximum authority Google grants, not the SkyTwin behavior supported by this release. SkyTwin's claimed live path reads Gmail metadata and message content, ingests Calendar context, maintains an account-bound history cursor, refreshes OAuth tokens, and records connector health. It does not claim supported Gmail sending or archiving, or supported Calendar mutation. Do not assume that an approved proposal changed the provider.

Disconnect or recover

Revoke the grant at Google Account → Third-party access. If Google reports invalid_grant, reconnect; testing-mode expiry, password/security changes, or manual revocation can invalidate the refresh token.

A successful personal BYO connection is not evidence that Google approved a SkyTwin-managed client. See the managed-client verification plan, privacy details, and Google's API Services User Data Policy.
